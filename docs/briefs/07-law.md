## Data (`prisma/schema/law.prisma`; additive migration `law`)
- `LawContentVersion` – an installed legal-content package (library version `YYYY.Qn`, rank, release date, summary). `content` Json holds the WHOLE library at that version (legislation + checklists, merged with the previous version); `changes` Json lists New/Amended items. Tenant-scoped (each tenant installs packages); profiles point at the version they accepted, so screens show the accepted content, never silently the newest.
- `LawProfile` – name (unique per tenant), owner, site (placement: business unit + site), jurisdiction, activities[], description, shared/private, show rating, accepted `contentVersion`, `version`, `archivedAt`.
- `LawRequirement` – one row per profile × checklist (kind CONTENT, `contentKey` = checklist key) or a company-specific "other requirement" (kind OTHER, own title/text/category/keywords). Rows are created when a checklist first applies (profile create/edit/accept) and are never deleted: a row that no longer applies shows under "Outside this profile" with all its work. Holds the evaluation: relevant + exclusion reason, "Why it applies / controls" and "How we checked / evidence" narratives, optional rating 0–100, owner, department (placement), next review date, evaluated date, `reviewRequired` (+ reason), captured Law form snapshot + answers, `version`, `archivedAt` (OTHER only). Reference `legal-evaluation` numbering (LEV-2026-0001). Title/register/category are copied from the accepted content for SQL filters and labels.
- `LawTask` – requirement task: reference (`law-task` → LT-2026-0001), title, details, owner, department (placement), due date, priority LOW/MEDIUM/HIGH, status OPEN/COMPLETED, completion comment/date, `archivedAt`, `version`.
- `LawLink` – explicit association requirement ↔ RiskAssessment / Incident / CorrectiveAction with context text; unique per (requirement, target). Raised follow-ups (incident draft, corrective action) go through the Incident follow-up contract (RecordLink, idempotent).

- `src/server/modules/law/workflow.ts`: evaluation status (Not relevant / Review needed / Checked / Partly checked / Not checked – "Checked" needs both narratives + owner + department + next review date and no review flag); save gates (exclusion reason, whole-number rating 0–100, valid dates); a review flag clears only with an explicit "I reviewed" confirmation on a complete evaluation; summary maths (relevant total, complete, excluded, review attention = flag or overdue review date, rating average of rated relevant items rounded, coverage, null = Not assessed); task gates (title, owner, due date; completion comment); next step + stepper.
- Access (`law-access.policy.ts`, Specification pattern): see = `law.view` in scope on shared profiles, OR `law.requirement.manage` in scope (also private), OR profile owner / requirement owner (/ task owner or creator for tasks). Evaluate, add tasks, link records, raise follow-ups = `law.evaluation.create` in scope OR requirement owner OR profile owner. Confirm a content-change review = `law.evaluation.approve` in scope OR requirement / profile owner. Profiles and other requirements = `law.requirement.manage` at the site; installing content = that permission company-wide. 404 outside scope.
- Follow-ups: Raise incident → `raiseIncidentDraft` type `non-compliance` (Law owns this type: Configuration → Law sets it up / switches it on; missing type or form blocks with guidance). Raise action → `raiseAction` corrective action with legal provenance (department in the profile's site, owner, due date); double submits deduped by a request key. Nothing a follow-up does changes the evaluation, rating or review flag.
- Due work: `law.evaluation` (relevant requirements with a next review date → owner, fallback profile owner) and `law.task` (open tasks → owner); seed adds them to the daily overdue job.
